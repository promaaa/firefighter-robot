# MotorTestGUI

실물 로봇과 시뮬레이션(MuJoCo)이 같게 세팅됐는지 확인하는 프로그램입니다. 관절 방향과 영점을 맞추고, 모터를 조금씩 움직여 볼 수 있습니다. 하네스에 매단 채 걷는 듯한 동작을 하는 보행 테스트(7절)도 있습니다.

- 왼쪽 3D: 실물 로봇. CAN으로 읽은 엔코더 값을 관절 각도로 바꿔 수업 모델(Robot Model v1)에 입힌 그림입니다.
- 가운데 3D: 시뮬레이션. 몸통을 고정한 같은 모델이 실물과 같은 목표 궤적을 받아 움직입니다.
- 오른쪽 패널: 관절 선택, 실시간 그래프(각도·속도·토크), 명령 탭(토크 켜기·힘 풀기, 상대·절대 이동), 영점·방향 설정 탭.
- 위쪽 줄: CAN 연결 상태(CANable 1~2개), 노드 12개 상태, Vbus, 버스 점유율, 빨간 **모두 힘 풀기 (Esc)** 버튼.

이 노트북(Windows, PowerShell) 기준으로 썼습니다.

| `--connect` | 저장된 CAN 설정으로 바로 연결 |
| `--config 파일` | 다른 설정 파일 사용 (기본 `config/robot_config.json`) |

## 3. 실물 로봇 연결

1. 로봇을 받침대에 매답니다.
2. **다리를 곧게 편 자세(시뮬 0° 자세)** 로 두고 드라이버 전원을 켭니다. 이유는 6절 "24° 문제"에 있습니다.
3. CANable을 노트북 USB에 꽂습니다. 두 개면 둘 다 꽂습니다.
4. 프로그램 위쪽에서 고릅니다.
   - **CAN 어댑터**: `slcan (CANable 출고 펌웨어, COM)`
   - **포트 1·2**: CANable이 꽂힌 COM 포트. 목록에 "CANable"이라고 나오고, 안 보이면 ↻를 누릅니다.
     - CANable이 두 개면 포트 1과 포트 2에 하나씩 고릅니다. 처음 실행할 때는 찾은 순서대로 자동으로 들어갑니다.
     - 하나만 쓰면 포트 2는 **(사용 안 함)**으로 둡니다.
   - **속도**: `500 kbps` (두 버스 모두 같은 속도)
5. **연결**을 누릅니다. 위쪽 노드 표시가 초록(힘 풀림)이 되는지 봅니다. 회색은 응답 없음입니다.

연결해도 토크는 켜지지 않습니다. 프로그램은 값을 읽는 요청만 보냅니다.
- 연결할 때 이미 토크가 켜진 보드가 있으면(다른 스크립트가 켜 둔 채 끝난 경우 등) 프로그램이 바로 힘을 풀고 경고를 띄웁니다.
- 토크는 관절을 고르고 **토크 켜기**를 눌렀을 때 그 관절에만 켜집니다.

### CANable 두 개 (CAN 버스 2개)

왼다리와 오른다리가 서로 다른 CAN 버스에 있고 CANable이 버스마다 하나씩이면, 둘을 **동시에** 연결해서 12개 관절을 한 화면에서 다룹니다.

- **포트 1이 왼다리일 필요는 없습니다.** 어느 노드가 어느 버스에 있는지는 연결하면 그 노드의 응답이 들어오는 버스를 보고 자동으로 알아냅니다. 그 노드에 보내는 명령은 그 버스로만 갑니다.
- 노드 번호는 두 다리 사이에 겹치지 않아야 합니다. 지금은 왼다리 1·3·5·7·11·13, 오른다리 2·4·6·8·12·14입니다.
- 어느 COM 포트가 어느 다리인지는 화면에서 보입니다.
  - 관절 표의 **node** 칸: "7 · 버스1"
  - 위쪽 노드 버튼에 마우스를 올리면: "버스 1 (COM5)"
  - COM 번호는 USB 포트를 바꿔 꽂으면 달라질 수 있지만, 자동으로 다시 알아내니 신경 쓰지 않아도 됩니다.
- 위쪽 통계 줄에 버스별 점유율과 노드 수가 나옵니다. 예: "버스1 16% (6개) · 버스2 15% (6개)". 한 버스에 12개를 다 물렸을 때보다 버스당 부하가 절반쯤입니다.
- 응답이 끊긴 노드를 찾는 요청과 **모두 힘 풀기(Esc)** 는 두 버스 모두에 보냅니다.

하드웨어 확인:
- 버스마다 양 끝(CANable 쪽과 그 버스의 마지막 드라이버 쪽)에 120 Ω 종단이 있어야 합니다.
- CANable 두 개를 **같은 버스**에 물리면 안 됩니다. 그러면 같은 노드 응답이 두 버스에서 다 들어오고, 프로그램이 "양쪽에서 들어옵니다" 경고를 띄웁니다.

CANable이 하나뿐이라 한 다리씩 작업할 때는, 한 다리를 끝내고 **설정 저장** → **끊기** → 다른 다리 버스에 꽂고 **연결**합니다. 다시 연결할 때는 그 다리를 곧게 편 자세로 둡니다. 연결할 때마다 24° 단위를 다시 고르기 때문입니다 (6절).

### Radxa 경유 (CANable을 Radxa에 꽂고 PC는 랜선으로)

```
PC (이 GUI) ──랜선·SSH──> Radxa (중계 프로그램) ──USB──> CANable ×2 ──CAN──> 드라이버 12개
```

GUI가 보내던 CAN 프레임을 그대로 Radxa로 보내고, Radxa의 작은 중계 프로그램(`radxa/can_bridge.py`)이 CANable로 내보냅니다. 응답도 같은 길로 돌아옵니다. 그래서 영점, 방향, 보호 정지, 보행 테스트가 노트북 직결 때와 똑같이 동작합니다.

**준비 (처음 한 번)**
- Radxa 전원을 켜고 랜선을 연결합니다. 노트북 **인터넷 연결 공유**가 이더넷에 켜져 있어야 합니다(저장소 루트 `CLAUDE.md`의 Radxa 절).
- PowerShell에서 아래 명령이 비밀번호를 묻지 않고 `rock-3c`를 출력하면 됩니다. 이 노트북에는 SSH 키가 등록돼 있습니다. 다른 PC는 그 PC의 키를 Radxa에 따로 등록해야 합니다.

  ```powershell
  ssh radxa hostname
  ```

- Radxa에는 아무것도 설치하지 않아도 됩니다. 중계 프로그램은 Python 3 표준 라이브러리만 씁니다.

**사용**
1. CANable 두 개를 **Radxa의 USB**에 꽂습니다. 노트북에는 꽂지 않습니다.
2. 다리를 곧게 편 자세로 드라이버 전원을 켭니다.
3. GUI를 실행합니다.

   ```powershell
   & "$env:USERPROFILE\odrv051\Scripts\Activate.ps1"
   cd "$env:USERPROFILE\Desktop\ASMR_ActuatorTest\MotorTestGUI"
   python motor_test_gui.py
   ```

4. 위쪽에서 **Radxa 경유**를 체크합니다. 포트 칸은 **(Radxa에서 자동)**이 됩니다. Radxa에 꽂힌 CANable을 모두 자동으로 찾습니다.
5. 오른쪽 주소 칸은 비워 두거나 `radxa`로 둡니다(SSH 별칭, = `rock-3c.local`). 속도는 `500 kbps`.
6. **연결**을 누릅니다. 몇 초 걸립니다. 그동안 GUI가 SSH로 중계 프로그램을 Radxa의 `~/motor_bridge/`에 복사하고, SSH 터널을 통해 실행·접속합니다.
7. 위쪽에 **실물 로봇 연결됨 (Radxa 경유)**가 나오고, 노드 12개가 초록이 되면 됩니다. 통계 줄 끝의 **Radxa 왕복 … ms**가 PC–Radxa 사이 왕복 시간입니다.

끝낼 때는 **끊기**를 누릅니다. 노트북 직결로 돌아가려면 **Radxa 경유** 체크를 풀고, CANable을 노트북에 꽂은 뒤 포트를 고릅니다. 체크 상태와 주소는 **설정 저장** 때 함께 저장됩니다.

**안전 (Radxa 쪽에서 따로 지킴)**
- 연결만으로는 토크가 켜지지 않습니다. 중계 프로그램은 스스로 명령을 보내지 않고, GUI가 보낸 프레임만 넘깁니다.
- **GUI에서 0.5초 동안 아무것도 안 오면**(PC가 멈추거나 랜선이 빠지면) 중계 프로그램이 본 적 있는 모든 node에 IDLE을 보냅니다.
- GUI 연결이 끊기거나 SSH가 끊겨도 IDLE을 보내고, SSH가 끊기면 중계 프로그램도 끝납니다.
- Esc / 빨간 **모두 힘 풀기**는 직결 때와 같습니다.
- 중계는 Radxa 안에서만 접속을 받습니다(SSH 터널). 네트워크에 포트를 열지 않습니다.

**알아 둘 점**
- 제어 계산(폴링, 보호 정지, 보행 궤적)은 지금도 **PC에서** 합니다. Radxa는 프레임만 넘기므로 랜선 지연(보통 1 ms 안팎)이 더해집니다. 나중에 정책을 로봇에서 돌리려면 그 계산을 Radxa로 옮겨야 합니다.
- 노트북 안에서 가상 로봇으로 시험했을 때 폴링 50 Hz, 엔코더 요청→응답 약 1.2 ms였습니다. 실제 Radxa에서의 값은 아직 재지 않았습니다.

**직접 실행 (문제를 찾을 때)**: Radxa에 SSH로 들어가 중계 프로그램을 직접 띄우고, GUI 주소 칸에 `tcp://IP:포트`를 넣으면 SSH 없이 붙습니다. 이 방법은 같은 네트워크의 누구나 접속할 수 있으니 시험할 때만 씁니다.

```powershell
ssh radxa
python3 ~/motor_bridge/can_bridge.py --listen 0.0.0.0:7700
```

GUI 주소 칸에는 `tcp://192.168.137.188:7700`처럼 Radxa 주소를 넣습니다(주소는 `Resolve-DnsName rock-3c.local`로 확인).

## 4. 방향 확인

관절 각도는 `방향 × (모터 위치 − 영점) ÷ 15`로 계산합니다. 방향이 틀리면 화면에서는 명령을 잘 따르는 것처럼 보이다가 실물은 기구 끝에 부딪힙니다. 영점보다 먼저, 또는 함께 확인합니다.

1. 다리를 곧게 펴고, **영점·방향 설정** 탭에서 **모든 관절 지금 = 0°**를 누릅니다. 대략적인 영점입니다.
2. 오른쪽 위에서 관절을 고릅니다.
3. **명령** 탭에서 **토크 켜기**를 누르고 **+5°**를 누릅니다.
4. 3D 화면에서 확인합니다.
   - 노란 화살표가 회전축, 노란 호가 + 방향입니다 (오른손 법칙: 엄지 = 화살표, 손가락이 감기는 쪽 = +).
   - 실물이 왼쪽 그림과 같은 쪽으로 움직였으면 방향이 맞습니다.
5. 반대로 움직였으면 **힘 풀기**를 누르고, **영점·방향 설정** 탭에서 방향을 **−1**로 바꿉니다. 0° 자세에서 영점을 잡았다면 영점은 다시 잡지 않아도 됩니다. 바꾼 뒤 3~4를 다시 해서 같은 쪽으로 움직이는지 봅니다.
6. 같은 쪽으로 움직이면 방향 옆의 **실물로 확인함**을 체크합니다. 설정 파일에 날짜로 남고, 관절 표 방향 칸에 ✓가 붙습니다. 방향을 바꾸면 체크가 지워집니다. 12개를 모두 확인했으면 **방향 모두 확인함…**으로 한 번에 체크해도 됩니다.
7. 토크 그래프의 실측(파랑)과 시뮬(청록) 부호가 반대면 **토크 부호(Iq)**를 바꿉니다. 그래프 표시에만 쓰이는 값입니다.
8. 관절마다 반복하고 **설정 저장**을 누릅니다.

방향 값은 모든 실물 명령(이동, 보행 테스트)과 각도 읽기에 쓰입니다. 시뮬은 늘 MJCF 관절 기준으로 움직이고, 실물로 보낼 때만 방향·영점으로 바꿉니다. 그래서 방향이 저장돼 있고 맞으면 실물과 시뮬이 같은 쪽으로 움직입니다. 보행 테스트는 12개 모두 **실물로 확인함**이어야 시작합니다.

## 5. 영점 설정

영점은 프로그램 설정 파일 `config/robot_config.json`에 저장됩니다 (드라이버에 저장하지 않음). 두 가지 방법이 있습니다.

### 방법 A: 지금 자세를 영점으로

- 다리를 곧게 편 자세에서 **모든 관절 지금 = 0°**를 누릅니다.
- 관절 하나만 하려면 **지금 자세 =** 칸에 각도를 넣고 **영점 정하기**를 누릅니다.
- 정확도는 손으로 자세를 얼마나 맞췄느냐에 달렸습니다 (보통 1~2°).

### 방법 B: 범위 훑기 (기구 끝 기준, 더 정확)

**영점·방향 설정** 탭의 **범위 훑기** 줄에서 합니다.

1. 모든 관절의 힘을 풀고 **시작**을 누릅니다. 토크가 켜진 관절이 있으면 시작되지 않습니다.
2. 관절마다 손으로 **양쪽 기구 끝까지** 천천히 돌리고, 끝에서 가볍게 한 번씩 댑니다.
   - 관절 표 알림 칸에 "기록 폭 / 기구 폭"이 나옵니다.
   - 돌리는 관절 말고 다른 관절은 곧게 펴 둡니다.
   - 빨리 돌리면 모터가 발전기처럼 전압을 만듭니다. 특히 12 V 파워서플라이를 쓸 때는 천천히 돌립니다.
3. 다리를 곧게 펴 두고 **끝 → 영점 계산**을 누릅니다.
4. 결과 창을 봅니다.
   - **지금 각도**가 0° 근처인지 확인합니다. 무릎이 −140°처럼 크게 다르면 방향이 반대입니다.
   - 체크된 관절만 적용됩니다. 기록 폭과 기구 폭이 3° 안으로 맞는 관절이 기본으로 체크됩니다.
5. **체크한 관절에 영점 적용**을 누르고, **설정 저장**을 누릅니다.

관절별로 쓸 수 있는 정도가 다릅니다. 기구 끝 각도는 수업 모델 메쉬 충돌 검사 결과입니다.

| 관절 | 기구 끝 | 범위 훑기 |
|---|---|---|
| knee, ankle pitch, ankle roll | 시뮬 범위 끝과 같음 | 양 끝 평균으로 계산 (가장 정확) |
| hip pitch | 시뮬 범위보다 19~24° 바깥 | 양 끝 평균으로 계산 |
| hip yaw | 한쪽만 (몸통 프레임에 닿음) | 기본 체크 안 함. 그 끝까지 댔다면 직접 체크 |
| hip roll | 없음 | 쓸 수 없음 → 방법 A |

- hip yaw는 두 다리를 곧게 두면 반대쪽 발목에 먼저 닿습니다. 반대쪽 다리를 벌려 두고 돌립니다.
- 실물의 기구 끝이 다르게 나오면 `config/robot_config.json`에서 관절마다 `stop_lo_deg` / `stop_hi_deg`를 고칩니다.

## 6. 다음에 켤 때 (24° 문제)

코스 펌웨어는 전원을 켤 때 모터 한 바퀴 안의 위치만 압니다. 감속비가 15라서 모터 한 바퀴는 관절 24°입니다. 그래서 프로그램은 **처음 보드를 볼 때(연결할 때, 또는 연결된 상태에서 드라이버를 켤 때) 관절이 기준 자세(기본 0°) ±12° 안에 있다고 보고** 24° 칸을 고릅니다.

- 저장한 영점은 계속 유효합니다. 다시 잡을 필요가 없습니다. 모터나 링크를 분해·재조립했을 때만 다시 잡습니다.
- 매번 **다리를 곧게 편 자세에서 연결**하면 각도가 바로 맞습니다.
- 어떤 관절이 정확히 24°쯤 틀려 보이면, 그 관절을 0° 근처로 옮기고 **각도 다시 맞추기**(전체는 **모두 다시 맞추기**)를 누릅니다.
- 항상 다른 자세에서 켠다면 **전원 켤 때 기준 자세** 값을 그 자세 각도로 바꿉니다.

## 7. 보행 테스트 (미팅 시연용)

하네스에 매단 로봇이 "저벅저벅" 걷는 동작을 합니다. 규칙으로 만든 동작이라 균형이나 지면은 다루지 않습니다. "보행 동작을 할 하드웨어 세팅이 끝났다"를 보이는 용도입니다.

### 동작

관절 각도를 직접 흔드는 대신 **발목 위치의 궤적**을 정하고, 다리 치수(허벅지 15.0 cm, 정강이 16.0 cm, 수업 모델에서 읽음)로 역기구학을 풀어 고관절·무릎 각도를 구합니다.

- **디딤** (기본 주기의 60%): 발이 땅에 붙은 것처럼 일정한 높이에서 엉덩이 아래를 앞→뒤로 등속으로 미끄러집니다. 발바닥은 평평합니다.
- **흔듦** (나머지 40%): 발을 들어(기본 3 cm) 앞으로 옮겨 내려놓습니다. 발의 속도가 디딤과 이어지게 만들어 착지·이륙이 매끄럽습니다. 무릎을 굽혀 발을 들 때는 발끝이 자연스럽게 처집니다.
- **발목**: 뒤꿈치 착지 → 발바닥 평평 → 뒤꿈치 들기 → 발끝 밀기.
- 두 다리는 반 주기 차이이고, 디딤 비율이 50%보다 커서 두 발이 같이 딛는 구간이 있습니다.
- 고관절 롤로 디딤 다리 쪽으로 몸을 조금 옮기고(±3°), 발목 롤이 발바닥 기울기를 되돌립니다. hip yaw는 움직이지 않습니다.
- 기본값(50걸음/분, 보폭 10 cm, 발 높이 3 cm)에서 관절 최고 속도는 약 136°/s(무릎)입니다. 탭의 미리보기 줄에 설정별로 나옵니다.
- 목표는 시뮬 관절 범위 2° 안쪽을 넘지 않게 부드럽게 누릅니다. 실물에는 위치 목표와 함께 속도 피드포워드를 보내 추종 지연을 줄입니다. 가상 로봇 시험에서 추종 오차는 최대 약 2.5°였습니다.
- 관절 목표는 시뮬(MJCF) 기준 각도이고, 실물에는 설정 파일의 **방향·영점**으로 바꿔 보냅니다(4절).

### 걸음 속도

- **걸음 속도**(걸음/분)가 다리가 얼마나 빨리 움직이는지를 정합니다. 한 발 = 한 걸음이라 한 주기(왼발·오른발)는 `120 ÷ 걸음 속도`초입니다. 50걸음/분이면 2.4초입니다.
- 미리보기 줄의 **가상 보행 속도**는 바닥 위였다면 몸이 나아갔을 속도(보폭 ÷ 디딤 시간)입니다. 기본값에서 약 0.07 m/s입니다. 매달려 있으니 실제로는 제자리입니다.
- 걷는 중에도 **걸음 속도**와 **진폭 배율**은 바꿀 수 있습니다(1초에 걸쳐 부드럽게). 관절 최고 속도가 300°/s를 넘거나 다리가 다 펴지는 설정은 시작·변경을 막습니다.

### 시작 전 조건

- 노드 12개가 모두 초록입니다(위쪽 노드 표시).
- 12개 관절 모두 영점이 있습니다(3D 그림에 보라색 관절 없음).
- 12개 관절 모두 **실물로 확인함**입니다(관절 표 방향 칸에 ✓, 4절).
- 에러가 없습니다.
- 로봇이 하네스에 매달려 있고, 발이 바닥·받침대에 닿지 않습니다. 다리 주변에 사람·물건·케이블이 없습니다. 다리를 들 때 발이 앞으로 약 10 cm, 위로 약 3 cm 움직입니다.

### 순서

1. GUI를 실행합니다.

   ```powershell
   & "$env:USERPROFILE\odrv051\Scripts\Activate.ps1"
   cd "$env:USERPROFILE\Desktop\ASMR_ActuatorTest\MotorTestGUI"
   python motor_test_gui.py
   ```

2. 위쪽에서 포트 1(왼다리 CANable, 예: COM16)과 포트 2(오른다리, 예: COM17)를 고르고 **연결**을 누릅니다. 노드 12개가 초록이 되는지 봅니다.
3. 오른쪽 아래 **보행 테스트** 탭을 엽니다. 상태 줄에 `시작하면: 실물 12개 관절 + 시뮬`이 나오고, 그 아래에 ⚠ 줄이 없어야 합니다. ⚠ 줄에는 시작할 수 없는 이유(응답 없는 관절, 영점 없음, 방향 미확인, 에러)가 나옵니다. ※ 줄은 알림입니다(예: 영점·방향 변경을 아직 저장 안 함).
4. 처음 한 번은 **진폭 배율**을 50%, **걸음 속도**를 40걸음/분 정도로 낮춰서 해 보기를 권합니다.
5. **▶ 보행 테스트 시작**을 누릅니다. 확인 창의 점검 항목과 **관절 방향**(설정 파일 값)을 확인한 뒤 **Yes**를 누릅니다.
6. 진행 순서: 12개 관절 토크 켜기(지금 자세 유지) → 준비 자세로 이동(약 2초, 무릎을 굽혀 발을 엉덩이 아래에) → 걷기(처음 2주기 동안 진폭을 키움) → 정한 시간이 지나면 한 주기 동안 진폭을 줄임 → 처음 자세로 돌아감 → 모두 힘 풀기.
7. 걷는 동안 **걸음 속도**와 **진폭 배율**은 바꿀 수 있습니다. 다른 설정은 멈춘 뒤에 바꿉니다.
8. 멈출 때:
   - **천천히 멈추기**: 진폭을 줄이고 처음 자세로 돌아간 뒤 힘을 풉니다.
   - **비상: Esc 또는 빨간 모두 힘 풀기**: 즉시 모든 관절을 IDLE로 둡니다(가상 로봇 시험에서 1~12 ms). 다리가 중력으로 떨어집니다.

걷는 동안에는 관절별 명령과 영점·방향 변경이 잠깁니다. 한 관절의 **힘 풀기**는 누를 수 있고, 누르면 보행 전체가 중단되며 모두 힘이 풀립니다.

### 설정

| 항목 | 기본 | 뜻 |
|---|---|---|
| 걸음 속도 | 50 걸음/분 | 1분에 몇 걸음 (30~80). 주기 = 120 ÷ 걸음 속도 (걷는 중 변경 가능) |
| 진폭 배율 | 100 % | 보폭·발 높이·좌우·발목 동작에 곱함, 최대 130 % (걷는 중 변경 가능) |
| 보폭 | 10 cm | 디딤 동안 발이 엉덩이 아래에서 앞→뒤로 미끄러지는 거리 |
| 발 들기 높이 | 3 cm | 흔듦 구간에 발을 드는 높이. 클수록 무릎을 높이 들고 빨라짐 |
| 무릎 기본 굽힘 | 25° | 기본 자세의 무릎 굽힘. 클수록 보폭·발 높이 여유가 커짐 (보폭 14 cm는 35° 정도 필요) |
| 디딤 비율 | 60 % | 한 다리가 땅을 딛는 시간 비율. 클수록 차분하고, 흔듦이 짧아져 다리를 빨리 듦 |
| 발목 쓰기 | 0.6 | 0이면 발바닥 늘 평평, 1이면 뒤꿈치 착지(6°)·발끝 밀기(12°)를 크게 |
| 좌우 흔들기 ± | 3° | 고관절 롤 진폭 (디딤 다리 쪽으로, 두 다리 같은 쪽) |
| 걷는 시간 | 30 s | 0이면 **천천히 멈추기**를 누를 때까지 |
| 끝나면 처음 자세로 돌아와 모두 힘 풀기 | 켬 | 끄면 처음 자세에서 토크를 유지 |

설정을 바꾸면 미리보기 줄에 한 주기 시간, 가상 보행 속도, 관절 최고 속도가 바로 나옵니다. 180°/s를 넘으면 주황, 300°/s를 넘으면 빨강이고 시작할 수 없습니다.

### 자동 중단

아래 중 하나라도 생기면 보행을 바로 끝내고 모든 관절 힘을 풉니다. 이유는 탭 상태 줄과 기록에 남습니다.

- 어느 관절이든 보호 정지 (목표-실측 10° 넘게 0.5초, 또는 |Iq| 8 A 넘게 1초)
- 응답 끊김, 드라이버 에러, 위치 제어가 풀림
- 토크를 켠 뒤 2.5초 안에 12개가 모두 위치 제어로 들어가지 않음
- 연결 끊기

### 시뮬로 미리 보기

실물을 연결하지 않았거나 명령 탭의 **실물에 보내기**를 끄면 시뮬에서만 움직입니다(확인 창 없음).

장치 없이 CAN 통신까지 연습하려면 가상 로봇으로 실행합니다. 이때는 **실물 설정 파일과 다른 설정 파일**을 씁니다. 가상 로봇에서 영점을 잡고 저장하면 실물 영점(`config/robot_config.json`)이 덮어써지기 때문입니다.

```powershell
& "$env:USERPROFILE\odrv051\Scripts\Activate.ps1"
cd "$env:USERPROFILE\Desktop\ASMR_ActuatorTest\MotorTestGUI"
python motor_test_gui.py --virtual --config "$env:TEMP\motor_test_gui_virtual.json"
```

가상 로봇은 다리를 곧게 늘어뜨린 채 시작하고, 모터 방향은 설정 파일의 방향을 그대로 따릅니다(`--virtual-flip`으로 고른 관절만 설정과 반대). **영점·방향 설정** 탭에서 **모든 관절 지금 = 0°**와 **방향 모두 확인함…**을 누른 뒤 보행 테스트를 시작합니다.

### 기록

매 실행이 `MotorTestGUI\logs\walk_날짜_시각\`에 자동으로 남습니다. 탭의 **기록 폴더 열기**를 누르면 마지막 기록 폴더가 열립니다.

## 8. 안전

- **Esc** 또는 빨간 **모두 힘 풀기** 버튼은 모든 노드를 IDLE로 둡니다. 진짜 비상 정지는 전원 스위치로 합니다.
- 한 번 명령은 **한 번 최대**(기본 30°)까지만 움직입니다. 영점이 있으면 목표를 시뮬 관절 범위에서 2° 안쪽으로 자릅니다.
- **보호 정지**: 목표와 실측 차이가 10°를 넘는 상태가 0.5초 넘게 가거나, 전류가 8 A를 넘는 상태가 1초 넘게 가면 그 관절만 IDLE이 됩니다. 방향이 틀린 관절이 기구 끝을 밀어붙이는 것을 막기 위한 장치입니다.
- 창을 닫을 때 토크가 켜진 관절이 있으면 힘을 풀지 묻습니다. "끊기"를 누르면 모두 힘을 풉니다.

## 9. 문제 해결

| 증상 | 확인 |
|---|---|
| 연결 실패 | COM 포트가 맞는지, 다른 프로그램(odrivetool, 시리얼 터미널, BasicTest 스크립트)이 그 포트를 잡고 있지 않은지. 메시지에 "포트 1"/"포트 2" 중 어느 쪽이 실패했는지 나옴 |
| "포트 1과 포트 2가 같습니다" | 포트 2를 두 번째 CANable로 바꾸거나 **(사용 안 함)**으로 |
| 노드 몇 개만 회색(없음) | 그 드라이버 전원, CAN 배선, node ID |
| 한쪽 다리 노드가 전부 회색 | 그 다리 버스의 CANable을 포트 2에 안 넣었거나(**사용 안 함**), 그 버스의 전원·배선·종단 문제 |
| "양쪽 버스에서 들어옵니다" 경고 | CANable 두 개가 같은 버스에 물림, 또는 두 버스에 같은 node ID 보드가 있음 (3절) |
| 각도가 24°쯤 틀림 | 6절 "각도 다시 맞추기" |
| 범위 훑기 "폭 불일치" | 끝까지 안 갔거나 다른 링크에 먼저 닿음. 계속 같으면 실물 기구 끝이 모델과 다른 것이니 `stop_lo_deg`/`stop_hi_deg` 확인 |

| 설정이 사라짐 | **설정 저장**(Ctrl+S)을 눌러야 파일에 남음. 종료할 때 저장 안 했으면 물어봄 |
| 보행 테스트 시작 버튼을 눌러도 시작 안 됨 | 탭 상태 줄의 ⚠ 이유 (응답 없는 관절, 영점 없음, 에러, 가동범위 기록 중) |
| "방향을 실물로 확인하지 않은 관절" | 4절대로 +5° 시험 후 **실물로 확인함** 체크 (또는 **방향 모두 확인함…**), **설정 저장** |

| 보행 시작 전 "다리가 다 펴집니다" / "최고 속도가 300°/s를 넘습니다" | 보폭·발 높이·걸음 속도·진폭 배율을 줄이거나 무릎 기본 굽힘을 늘림 |
| Radxa 경유: "SSH로 접속하지 못했습니다" | Radxa 전원·랜선, 노트북 이더넷 주소가 192.168.137.1인지(인터넷 연결 공유), PowerShell에서 `ssh radxa hostname`이 되는지. 자세한 순서는 저장소 루트 `CLAUDE.md`의 "연결이 안 될 때" |
| Radxa 경유: "Radxa에 CANable(USB 16d0:117e)이 없습니다" | CANable을 Radxa USB에 꽂았는지. `ssh radxa "ls -l /dev/ttyACM*"`로 장치가 보이는지 |

| Radxa 경유: "다른 GUI가 이미 연결되어 있습니다" / "Device or resource busy" | 다른 PC의 GUI나 남은 중계 프로그램이 CANable을 잡고 있음. 그 GUI를 끊거나 `ssh radxa "pkill -f can_bridge.py"` |
| Radxa 경유: 연결 중 "Radxa 감시: GUI 응답이 0.5 s 끊겨 모두 힘 풀기" | PC가 잠깐 멈췄거나 랜선이 불안정. 토크가 풀렸으니 원인을 확인하고 다시 토크 켜기 |
| 보행 중 특정 관절에서 보호 정지 | 그 실행의 `events.txt`에서 `[CAN] ⚠ … 보호 정지` 줄과 `samples.csv`의 그 관절 열(목표·실측·Iq)을 봄. 진폭 배율을 낮춰 다시 |

## 10. 지연·관절 응답 실험 (Radxa에서)

Radxa에서 명령을 보냈을 때 실물 관절이 얼마나 늦게, 어떤 모양으로 반응하는지 잽니다. 목적은 새 시뮬을 실물에 맞춰 만드는 것입니다. 기존 학습 코드나 시뮬과는 비교하지 않고 실물 값만 잽니다.

| 시험 | 관절 움직임 | 재는 것 |
|---|---|---|
| `rtt` | 없음 | 엔코더 요청→응답 시간, 12개를 한꺼번에 읽는 시간, 읽은 값의 나이 |
| `loop` | 없음 | 제어 주기를 25~400 Hz로 바꿔 가며, 매 주기 '12개 읽기 + 목표 12개 보내기'가 몇 Hz까지 되는지 |
| `step` | 관절 하나 | 계단 목표를 줍니다. 명령 → 드라이버가 목표 적용(Iq 명령값 변화) → 실제 전류 → 움직임 시작까지의 시간, t10·t50·t90, 정착 시간, 오버슈트, '순수 지연 + 1차계' 맞춤, 목표 대비 끝 오차와 마찰 토크 |
| `sine` | 관절 하나 | 정한 명령 주기(`--hz`)로 사인 목표를 보냅니다. 주파수별 진폭비, 위상, 시간 지연 |

측정 도구 `radxa/latency_test.py`는 Radxa 안에서 CANable을 직접 엽니다 (표준 라이브러리만 사용). PC의 `latency/latency.py`가 이 도구를 Radxa에 복사해 실행하고, 기록을 가져와 분석합니다.

### 준비
- **GUI의 Radxa 경유 연결은 끊습니다.** 측정 도구가 CANable을 혼자 씁니다.
- CANable 두 개가 Radxa USB에 꽂혀 있어야 합니다.
- 로봇을 하네스에 매답니다. 다리를 편 자세에서 드라이버 전원을 켭니다 (24° 칸 때문).
- PowerShell에서 `ssh radxa hostname`을 실행해 `rock-3c`가 나오는지 확인합니다.
- 관절 설정(방향·영점·범위)은 `config/robot_config.json`에서 매번 다시 만들어 보냅니다. GUI에서 영점을 바꿨다면 먼저 **설정 저장**을 누릅니다.

### 순서 (PowerShell)

```powershell
& "$env:USERPROFILE\odrv051\Scripts\Activate.ps1"
cd "$env:USERPROFILE\Desktop\ASMR_ActuatorTest\MotorTestGUI"
```

1. 읽기만 하는 시험입니다. 관절은 움직이지 않습니다.

   ```powershell
   python latency\latency.py run rtt
   python latency\latency.py run loop
   ```

2. 관절 하나를 움직이는 시험입니다. 시작 전에 확인 질문이 나오고, `y`를 입력해야 움직입니다.

   ```powershell
   python latency\latency.py run step --joint left_knee_pitch --deg 4 --n 10 --tag 4deg
   python latency\latency.py run step --joint left_knee_pitch --deg 8 --n 10 --tag 8deg
   python latency\latency.py run step --joint left_ankle_pitch --deg 4
   python latency\latency.py run step --joint left_hip_pitch --deg 4
   python latency\latency.py run sine --joint left_knee_pitch --deg 4 --hz 50 --tag 50hz
   python latency\latency.py run sine --joint left_knee_pitch --deg 4 --hz 150 --tag 150hz
   ```

   - `step`: 그 관절만 위치 제어로 켭니다. 범위 안쪽 시작점에서 `--deg`(기본 4°, 최대 10°) 계단을 `--n`번 왕복합니다 (각 1초 유지). 그동안 엔코더와 Iq를 한꺼번에 요청해 둘 다 약 1~2 ms 간격으로 기록합니다. 약 25초 걸립니다.
   - `sine`: 가운데에서 ±`--deg`로 0.5·1·2·4·6 Hz를 4주기씩 줍니다 (앞뒤 1주기는 진폭을 키우고 줄임). 목표는 `--hz` 주기로 보냅니다. 약 27초 걸립니다.
   - 관절이 기구 끝(예: 쭉 편 무릎)에 기대 있어 범위 밖 6° 안에 있으면, 먼저 범위 안으로 천천히 옮긴 뒤 시작합니다. 6°보다 크게 벗어나면 24° 칸 오류로 보고 멈춥니다.
   - 오른다리는 `right_knee_pitch`처럼 씁니다. `--tag`는 기록 폴더 이름 끝에 붙습니다.
   - 확인 질문 없이 바로 실행하려면 `--yes`를 붙입니다. 관절 옆에 사람이 있을 때만 씁니다.
3. 결과를 한 표로 봅니다.

   ```powershell
   python latency\latency.py report
   ```

**안전**
- 움직이는 시험은 그 관절만 위치 제어로 켭니다. 나머지는 IDLE 그대로입니다.
- |Iq| > 8 A이거나 목표와 실측이 12° 넘게 벌어진 상태가 0.3초 이어지면 바로 IDLE로 바꿉니다.
- 끝나면 시작점(범위 안)으로 천천히 옮기고 IDLE로 바꿉니다.
- PC에서 **Ctrl+C**를 누르거나 SSH가 끊기면 Radxa 쪽에서 IDLE로 바꿉니다.

### 2026-11-20 결과

조건: 왼다리, slcan 펌웨어 CANable 두 개를 Radxa에 연결, 하네스에 매단 상태, 움직이는 관절 말고는 모두 IDLE, 강의 게인(무릎·고관절 Kp 100.6 Nm/rad · Kd 7.99 Nm·s/rad, 발목 71.6 / 3.58).

**통신과 제어 주기**

| 항목 | 값 |
|---|---|
| 엔코더 요청→응답 | 중앙값 1.73 ms, p95 2.2 ms |
| 12개 한꺼번에 읽기 | 중앙값 약 4 ms, p95 6 ms |
| '12개 읽기 + 목표 12개'가 되는 최대 주기 | 약 150 Hz (CAN 대역폭 한계, 190 Hz부터 읽기가 빠짐) |

**명령에서 움직임까지 (무릎·발목·고관절 같음)**

| 단계 | 명령 후 |
|---|---|
| 드라이버가 새 목표 적용 (Iq 명령값 변화) | 약 0.5 ms (표본 간격 때문에 0.4~1 ms 사이로만 알 수 있음) |
| 실제 전류가 따라옴 | 약 2 ms |
| 관절이 0.1° 움직이기 시작 | 약 4~6 ms (대부분 관성을 가속하는 시간) |

**계단 응답 (4°·8°, 양방향, 각 20번)**

| 관절 | 시간 상수 τ | 설정 Kd/Kp | 순수 지연 맞춤 | 마찰 토크 | 강의 MJCF frictionloss |
|---|---|---|---|---|---|
| 무릎 | 75~81 ms | 79 ms | 4~5 ms | 0.30 Nm | 0.377 |
| 고관절 피치 | 78~84 ms | 79 ms | 3~7 ms | 0.30~0.35 Nm | 0.377 |
| 발목 피치 | 43~48 ms | 50 ms | 4~6 ms | 0.37 Nm | 0.317 |

- 응답은 오버슈트 없는 1차계입니다. 진폭을 두 배로 해도 τ가 같습니다 (선형).
- 드라이버의 '위치 P → 속도 P' 구조는 토크 PD(τ = Kp·오차 − Kd·속도)와 같습니다. 그래서 τ ≈ Kd/Kp가 됩니다.
- 마찰 토크는 목표 대비 끝 오차의 두 방향 평균에 Kp를 곱한 값입니다. 출발점 기준 오차(`steady_err_deg`)는 출발점도 앞 계단에서 덜 온 자리라 이 값의 약 2배입니다.
- 관성 맞춤 (PD + 0.55 ms 지연 + 전류 지연 + 쿨롱 마찰, 링크 관성은 MJCF에서 다른 관절이 자유롭다고 놓고 계산):
  - 무릎 armature 0.022 (펴는 방향) / 0.031~0.034 (굽히는 방향). MJCF는 0.0228입니다.
  - 발목 armature 0.007~0.014. MJCF는 0.0056입니다.
  - 고관절은 하네스에 매달린 몸통이 같이 움직여서 이 방법으로는 구할 수 없습니다.
  - 다시 계산하려면 `python latency\fit_inertia.py <계단 폴더 이름> ...`을 실행합니다. 결과는 `logs\latency\model_fit.json`에 저장됩니다.
- 전체 결과 정리(영어, JSON 포함): [../results/real_actuator_20261120.md](../results/real_actuator_20261120.md)

**사인 응답 (무릎, ±4°)**

| 주파수 | 진폭비 50 Hz / 150 Hz | 위상 지연 50 Hz / 150 Hz | 1차계(τ 79 ms)만으로 |
|---|---|---|---|
| 0.5 Hz | 0.93 / 0.94 | 19° / 18° | 0.97, 14° |
| 1 Hz | 0.86 / 0.86 | 33° / 31° | 0.90, 27° |
| 2 Hz | 0.69 / 0.69 | 58° / 53° | 0.71, 45° |
| 4 Hz | 0.41 / 0.42 | 84° / 75° | 0.45, 63° |
| 6 Hz | 0.29 / 0.30 | 101° / 88° | 0.32, 72° |

- 1차계 위에 남는 지연 (2~6 Hz):
  - 50 Hz 명령: 14~18 ms
  - 150 Hz 명령: 7.7~11 ms
- 이 값은 '순수 지연 약 4.5 ms + 명령 주기의 반(50 Hz는 10 ms, 150 Hz는 3.3 ms)'과 맞습니다.
- 0.5~1 Hz에서 더 남는 지연(12~28 ms)은 느릴 때 마찰이 걸리는 효과로 보입니다.

**시뮬에 넣을 값 (제안)**
- 관절은 위 게인의 PD 토크로 넣습니다. 보행에서 가장 큰 지연은 이 PD의 1차 지연(τ ≈ 80 ms, 무릎·고관절 대역폭 약 2 Hz)입니다. 같은 게인과 맞는 관성을 쓰면 시뮬이 스스로 재현합니다.
- 명령 쪽 순수 지연은 약 1~2 ms(전송 0.5 ms + 전류 루프)입니다. 그 위에 정책 계산 시간과 명령 주기의 반을 더합니다.
- 관측 지연은 약 1~4 ms입니다 (요청→응답의 반 + 12개를 차례로 읽는 시간).
- frictionloss는 MJCF 값(0.3~0.38 Nm)이 실물과 비슷합니다.
- armature는 무릎·고관절 0.0228이 맞고, 발목은 MJCF보다 클 수 있습니다 (0.007~0.014 범위로 무작위화 제안).

**알아 둘 점**
- 지금 CANable은 **slcan 출고 펌웨어**입니다. 팀 런타임은 **candleLight 펌웨어 + SocketCAN**을 전제로 합니다. 둘은 USB 처리 방식이 달라 통신 지연이 다를 수 있으니, 펌웨어를 바꾸면 `rtt`·`loop`를 다시 합니다. 측정 도구는 `--socketcan can_left,can_right`로 SocketCAN도 엽니다.
- 분석은 드라이버 게인을 setup 백업 값으로 봅니다. 드라이버 게인을 바꿨다면 결과의 `driver_gains_assumed`가 실제와 달라지니 다시 맞춥니다.
- 2026-11-20 기준 양쪽 무릎이 영점보다 약 2.5° 더 펴진 자리(기구 끝)에서 쉽니다. CAD 무릎 끝은 0°입니다. 영점을 펴짐 끝에 맞춰 다시 잡거나(5장 범위 훑기), 시뮬의 무릎 한계를 실물에 맞춥니다.
